# MS #56 - First CloudBank Dark Factory Run

> **Status:** Complete
>
> **Release:** 0.56.0
>
> **Date:** 2026-09-02
>
> **Audience:** Customers, partners, executives, architects, delivery teams, and assurance reviewers

## Executive summary

MS #56 - First CloudBank Dark Factory Run converts a specific part of the LIGHTYEAR modernization approach into a governed, reviewable capability. Turns the customer mapping into an isolated, receipt-gated workcell that can prove one bounded Spring contract on Oracle and PostgreSQL without changing the pinned source.

## Why this matters to a customer

Turns the customer mapping into an isolated, receipt-gated workcell that can prove one bounded Spring contract on Oracle and PostgreSQL without changing the pinned source.

The practical result is a narrower, evidence-backed decision instead of a broad modernization claim. The milestone packages capability, proof, and limitations together so commercial, architecture, delivery, security, and assurance teams can review the same record.

## What the milestone delivers

- A sealed work order that copies the complete pinned cloudbank-v5 source into isolation and admits exactly six customer-service paths.
- Content-addressed templates for Maven, PostgreSQL datasource and Hibernate settings, Liquibase SQL, the JPA entity, and the shared test.
- A deterministic worker that rejects source drift and applies only the six edits through the existing patch broker.
- One shared Oracle and PostgreSQL Spring/JPA contract for four synthetic rows, defaults, empty strings, case-sensitive searches, CRUD, and owner/admin authorization.
- A baseline-first gate that passes unchanged source on the admitted Oracle image before testing the generated service on PostgreSQL 16.
- A signed receipt chained to the MS #54 and MS #55 receipts, immutable images, factory receipt, work order, mapping, and transformation plan.
- Ephemeral loopback-only ports and exclusion of credentials, raw Maven output, demonstration passwords, and production data.
- Cross-platform launchers, schemas, Control Tower status, CI checks, deterministic artifacts, and adversarial tests.

## How it differs from earlier work

MS #54 established signed Oracle evidence and MS #55 established the signed PostgreSQL mapping. MS #56 chains them into the first baseline-first CloudBank application transformation, limited to one synthetic customer-service contract.

Earlier work remains useful evidence, but it is not automatically promoted into this milestone. A successful parser, simulator, local comparison, or generated artifact is not presented as live platform equivalence or production readiness.

## What a customer can do with it

A customer can use first cloudbank dark factory run as a bounded decision and delivery capability. It can be attached to the customer's approved source package, owners, policies, target architecture, acceptance criteria, and authorized evidence.

Unresolved semantic loss, policy decisions, unsupported behavior, and live-evidence requirements remain visible rather than being averaged into one pass/fail statement.

## Evidence and acceptance posture

The milestone is complete as a repository capability because its committed implementation and release record are present. Customer qualification remains claim-specific: only the delivered behaviors listed above are supported, and only at the evidence class recorded by their underlying receipts and gates.

A customer review should confirm:

1. the exact source, graph, policy, fixture, and artifact identities referenced by the evidence;
2. the difference between deterministic development evidence and authorized live evidence;
3. every policy decision, lossy transformation, unsupported behavior, and explicit exclusion;
4. the acceptance gates that passed and the live or production gates that remain blocked; and
5. that later changes have not invalidated the content-addressed evidence.

## Boundaries and claims not made

- The committed readiness receipt is not evidence that the native dual run occurred.
- Execution requires operator-held signed MS #54 and MS #55 receipts plus the same verification key.
- A passing receipt proves only the declared synthetic customer-application contract.
- The shared parent still supplies Oracle libraries outside this six-file workcell.
- HTTP transport, concurrency, CDC, cutover, rollback, packaging, and production-shaped data remain outside this proof.
- Human promotion, whole-CloudBank equivalence, migration completion, production-data equivalence, and production readiness remain false.

These boundaries are part of the deliverable. They prevent bounded development evidence from becoming an unsupported customer promise.

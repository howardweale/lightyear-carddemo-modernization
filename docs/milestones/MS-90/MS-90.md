### Why this matters

A migration can produce the right business result while two engines print a number differently or store different time precision. A blanket normalization can hide a real defect. Leaving every representational difference unresolved can also obscure a valid result. MS90 makes the accepted boundary explicit, narrow, versioned and auditable.

The factory generated the candidate. The original deterministic judge exposed the differences. A person accepted a limited precision contract. A separately versioned deterministic judge then assessed the retained observations against that contract. The builder did not receive expected business outputs or edit its candidate during this reassessment.

### The observed business journey

Both native lanes completed the same partial-invoicing scenario. Three ordered units were shipped and invoiced in portions of one and two. The observed invoice totals were 19.35 and 38.69, including tax of 1.35 and 2.70. The original lane checks verified 28 accounting entries in 12 balanced groups per engine. Starting stock of ten became seven. These business checks and expected values were not relaxed.

## The precise comparison contract

### Numeric values: equality without rounding

Only `order.discount`, `order.reserved` and `shipment.delivered` receive the new numeric rule. Both strings must parse as finite decimal values, and their mathematical values must be exactly equal. The comparison uses decimal arithmetic, not binary floating point. It introduces no tolerance and performs no rounding.

| Field | Oracle | PostgreSQL | Version-2 treatment |
|---|---|---|---|
| `order.discount` | `10` | `10.00` | Equal exact decimal values |
| `order.reserved` | `3` | `3.0` | Equal exact decimal values |
| `shipment.delivered` | `3` | `3.0` | Equal exact decimal values |

For example, `10` and `10.000000000000001` still differ. `NaN`, infinity, missing values and whitespace-padded values are rejected. The rule is not applied globally to other amounts, invoice totals or arbitrary trace fields.

### Shipment dates: an owned precision decision

The signed decision `idempiere-oracle-date-seconds-v1` belongs to **Howard Weale**, takes effect on **26 September 2026**, and must be reviewed on **25 December 2026**. A new assessment on or after that review date is rejected until an appropriate renewed decision and versioned policy are supplied.

Its only column is `adempiere.m_inout.shipdate`, for the first and second shipments. The retained native catalogs and states show Oracle `DATE`, PostgreSQL `timestamp without time zone`, and UTC capture sessions on both sides. Each trace value must bind to the corresponding native shipment row and identifier.

The observed Oracle value is `2026-09-26T12:34:56`; PostgreSQL retains `2026-09-26T12:34:56.123456`. Version 2 admits that fractional loss only because the Oracle fraction is zero and every component through whole seconds matches. It never rounds into the next second.

### Boundaries that remain enforced

A different second, another column, a different native datatype, an unsupported timezone context, an invalid date, an offset-bearing value or a mismatched row identity is not admitted. Subsecond ordering, audit timing and service-level timing guarantees remain outside the accepted scope. The captured database-session facts do not establish arbitrary application-client or production timezone equivalence.

Two native row differences and two corresponding trace differences describe the same two shipment timestamps. Along with the three numeric trace differences, the new report admits five trace findings and two row witnesses. These are not seven independent defects. Every original value remains visible.

## Preservation and verification

### One evidence set, two labelled verdicts

The assessment command verifies the source run's signatures, authorization, journal chain, plan, cleanup and implementation hashes. It hashes the retained source files, copies them to a separate workspace, and reruns the unchanged original judge on that copy. This is a deterministic replay over recorded observations; no database is started.

The reproduced original gate must equal the original gate exactly. Only then can the new comparison run. Afterward, the command hashes the source files again and checks that the policy, decision and pinned implementation did not change. It refuses an existing output directory, keeping each publication separate.

The signed version-2 receipt reports both `original_gate_passed: false` and its own `passed: true`, together with `original_gate_reproduced: true` and `original_source_preserved: true`. The old run, original gate modules, candidate, observations and campaign accounting remain intact.

## Operating the assessment

### Verify the published result

From the repository root, with the project environment installed, run:

```powershell
$env:PYTHONPATH='src'
python tools/evaluate_journey_judge_v2.py verify `
  --output docs/calibration/idempiere-judge-v2
```

The expected status is `verified-versioned-assessment`, with `passed: true`, `original_gate_passed: false` and `full_native_gate_replayed: false`. Read the last field literally: this command verifies the published summaries and their signed lineage.

### Reassess retained native observations

For a fresh, separately signed assessment, the operator must have the original local run, trusted signing material, unchanged pinned implementation and an effective timestamp decision. Use a new output path:

```powershell
$env:PYTHONPATH='src'
$run='factory/idempiere/ms86-journeys/runs/'
$run+='journey-2ba2716e5c1749f89bdecd4cb1d17280'
python tools/evaluate_journey_judge_v2.py evaluate `
  --run $run `
  --output work/ms90/new-assessment
```

This copies the retained evidence, reruns the original deterministic gate, applies version 2 and signs a new assessment. An existing output directory is refused. Do not use the original verifier directly on the source run for this task: it writes derived summaries. Do not edit an old receipt to make its status pass.

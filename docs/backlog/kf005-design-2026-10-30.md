# KF-005 / REWRITE-109 fault-injection design

Backlog lane — document-only draft, 30 October 2026.

This is a proposal for a later, separately reviewed CI fixture. It contains no
implementation, new POSTTRAN attempt, source change, signature or fault execution.
The promotion blocker posttran-runtime-rewrite-109 remains OPEN. No run-bound or
POSTTRAN-frozen path is changed, and no work from the critical-path lane is used.

## Decision and question

Source: [Howard's KF-005 direction](https://github.com/howardweale/lightyear-carddemo-modernization/issues/436#issuecomment-6449509273).

The conversion disposition is KEEP source-faithful. The recommended post-cutover
FIX would be a different behavior change with separate customer sign-off and
verification. This design addresses only whether twin and candidate produce the
same source-faithful result on a controlled account REWRITE failure.

Required result: transaction written, TCATBAL updated, persisted account unchanged,
no reject record and no abend on the reason-109 path. A normal-path comparison,
compiler identity or earlier source-only argument cannot answer that question.

## Exact observation boundary

The public source's posting paragraph calls 2700 TCATBAL, 2800 account and then
2900 transaction in that order. At account REWRITE INVALID KEY, lines 554–558 set
reason 109 and its description. The account paragraph returns; the transaction
paragraph is still reached. The test must distinguish the in-memory account
calculation from the unchanged persisted account.

Planned: inject exactly one status-23 / INVALID KEY result at the account
REWRITE operation after the account read and TCATBAL update succeed. Do not
delete the account before lookup, fail its READ, corrupt a fixture or change
the source condition: those would exercise another path. The failed operation
must make no persisted account mutation. All later operations use normal I/O.

## Proposed seam — feasibility gate, not an existing capability claim

Preferred seam: a test-only I/O adapter around the actual account rewrite boundary,
with the same declared fault selection and observable event contract for twin and
candidate. Whether both implementations expose a suitable seam is NOT established.
A future implementation review must name the exact files and compare the real
call paths before choosing an adapter.

If compiled-twin instrumentation is necessary, it belongs only to an isolated
temporary CI build copy with an explicit before/after byte inventory. Label it
instrumented; retain the transformation, compiler/image and original source
identities. It must not replace the frozen source, weaken the comparator, or be
described as an unmodified executable. A candidate-side shortcut that bypasses
the real rewrite caller is not an acceptable matching fixture.

Not approved: any implementation path or executable hash under this document.
The future packet must bind its actual hook/harness/candidate/observer bytes
and scope in advance. Missing symmetric seams or trustworthy observations is a
design blocker, not permission for an unreviewed source edit.

## Small prospective case matrix

| Planned case | Purpose | Required distinguishing observation |
| --- | --- | --- |
| KF005-NORMAL | Positive control with injection disabled | Account, TCATBAL and transaction changes match the ordinary source-faithful result; no spurious reason 109. |
| KF005-REWRITE23 | One targeted account rewrite failure | Exactly one injection; TCATBAL changed; persisted account byte-identical; one transaction; no reject/abend; reason 109 and subsequent transaction write observable. |
| KF005-WRONG-FATAL | Negative control representing the deferred fatal behavior | The observer must distinguish an early fatal/abort outcome from the KEEP result. |
| KF005-WRONG-PERSIST | Negative control for a fake or misplaced fault | A changed persisted account or zero/multiple fault events must be distinguishable. |
| KF005-WRONG-ORDER | Negative control for incorrect partial-update sequencing | Missing TCATBAL update or transaction write must be distinguishable. |
| KF005-UNRELATED | Untargeted record/operation control | The selector must not leak into another record or operation; fresh state per case. |

The negative-control behaviors are observation requirements, not proposed
production algorithms or changes. Each control needs its own declared expected
difference. No case is a whole-program equivalence or release result.

## Inputs, records and invariants

- Planned: authored public synthetic input only, one targeted transaction/account
  and enough untouched sentinels to detect selector spillover. No Maintec,
  mLogica, CMS, customer, private expected or live database material.
- Planned: identical initial records, processing clock and all non-fault inputs
  for twin and candidate; bind exact byte hashes and complete key/count inventories.
- Planned: capture pre/post ACCTFILE, TCATBALF, TRANFILE and DALYREJS, all file and
  return statuses, and the minimal operation trace needed to show order and reason.
- Planned: record selector identity, target key/operation, one actual injected event,
  attempted rewrite, normal reads, TCATBAL write and subsequent transaction write.
- Planned: compare raw record identities and fields through the existing comparator,
  including every unchanged/sentinel record. Do not add a normalization or ignore
  a difference to make the path look equivalent.
- Planned: check that the normal control, fault case and all wrong controls are
  distinguishable before interpreting a twin/candidate match.
- Planned: retain incomplete, divergent, indeterminate and cleanup-failure outcomes.
  A missing trace or capture is incomplete evidence, not an equivalent result.

## CI and custody proposal

Planned: only after the 5 November run closes and the later exact implementation
packet receives separate review, use the smallest existing Linux fixture route.
No workflow edit, full Windows loop, external model or signature is part of this
design. Actual CI selection and resource limits belong to that later review.

Planned: retain the original source and register hashes before and after the
fixture, synthetic input/output inventories, compiler/runtime pins, transformation
identity if any, raw twin/candidate receipts, negative-control outcomes and
comparator result. Put large captures in the reviewed evidence store, with a
small committed manifest. Never overwrite historical attempt-1 evidence, reuse
its reservation/nonce, or change a consumed tag.

## Interpretation and closure

Planned: only the complete targeted observation set can support a request to
close this path blocker. Even identical outputs cannot compensate for no actual
injection or a different caller. A matching controlled fixture remains bounded
to that seam, source and input; it is not native VSAM or production-failure proof.

Planned: present the raw evidence and exact hashes to Howard for a separate
disposition. Keep the blocker open until that decision. The post-cutover FIX,
any new campaign and customer release require their own review and evidence.

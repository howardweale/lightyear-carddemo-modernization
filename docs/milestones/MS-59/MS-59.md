# MS #59 - CloudBank PostgreSQL Transaction-Core Factory Run

> **Status:** Complete
>

>

> **Audience:** Customers, partners, executives, architects, delivery teams, and assurance reviewers

## Executive summary

MS #59 - CloudBank PostgreSQL Transaction-Core Factory Run converts a specific part of the LIGHTYEAR modernization approach into a governed, reviewable capability. Turns the admitted Account and Transfer wave into reviewable target code and a native PostgreSQL money-movement gate while preserving the distinction between a passing target and cross-database equivalence.

## Why this matters to a customer

Turns the admitted Account and Transfer wave into reviewable target code and a native PostgreSQL money-movement gate while preserving the distinction between a passing target and cross-database equivalence.

The practical result is a narrower, evidence-backed decision instead of a broad modernization claim. The milestone packages capability, proof, and limitations together so commercial, architecture, delivery, security, and assurance teams can review the same record.

## What the milestone delivers

- A 20-path isolated transformation of the pinned root, Account, and Transfer source with exact source and template hashes.
- PostgreSQL Liquibase DDL for Accounts, Journal, and durable idempotent Transfer Commands using synthetic bootstrap data.
- A local atomic money-movement service that locks accounts in stable order and writes debit, credit, command state, and paired journals in one transaction.
- A Transfer facade that requires authentication and forwards an idempotency key, actor identity, and internal service token to Account.
- Retirement of the generated target's Oracle wallet/UCP, MicroTx LRA participants, and Account-local AQ grant script.
- Seven tests covering the eight admitted scenarios: successful value conservation, invalid amount, insufficient funds, authorization denial, duplicate suppression, injected crash rollback and retry, and journal replay.
- Executable Account and Transfer JAR inspection requiring zero Oracle and zero MicroTx runtime libraries.
- A signed MS #58-chained native PostgreSQL receipt, deterministic contracts, compatibility ledger, schemas, cross-platform launchers, documentation, and adversarial overclaim tests.

## How it differs from earlier work

MS #58 pinned the Account/Transfer source, mapped its schema, defined eight behaviors, and admitted the work. MS #59 executes that bounded target workcell and leaves Oracle comparison, messaging, the remaining services, and production operations for later evidence.

Earlier work remains useful evidence, but it is not automatically promoted into this milestone. A successful parser, simulator, local comparison, or generated artifact is not presented as live platform equivalence or production readiness.

## What a customer can do with it

A customer can use cloudbank postgresql transaction-core factory run as a bounded decision and delivery capability. It can be attached to the customer's approved source package, owners, policies, target architecture, acceptance criteria, and authorized evidence.

Unresolved semantic loss, policy decisions, unsupported behavior, and live-evidence requirements remain visible rather than being averaged into one pass/fail statement.

## Evidence and acceptance posture

The milestone is complete as a repository capability because its committed implementation and release record are present. Customer qualification remains claim-specific: only the delivered behaviors listed above are supported, and only at the evidence class recorded by their underlying receipts and gates.

A customer review should confirm:

1. the exact source, graph, policy, fixture, and artifact identities referenced by the evidence;
2. the difference between deterministic development evidence and authorized live evidence;
3. every policy decision, lossy transformation, unsupported behavior, and explicit exclusion;
4. the acceptance gates that passed and the live or production gates that remain blocked; and
5. that later changes have not invalidated the content-addressed evidence.

## Boundaries and claims not made

- The committed readiness receipt proves generated artifacts and readiness, not that an operator native run occurred.
- A passing execution receipt proves Account against native PostgreSQL and Transfer against an isolated facade contract; it does not prove a live two-service HTTP exchange.
- The full native transaction wave and LRA replacement remain false pending an integrated Account and Transfer run.
- The original Account and Transfer applications are not executed on Oracle in this milestone, so Oracle-to-PostgreSQL transaction equivalence remains false.
- Removing Account-local AQ grants does not migrate or qualify the Oracle AQ flow used by Checks.
- The remaining five unqualified deployable services are not transformed or executed.
- Production data is not accessed; only deterministic synthetic rows are used.
- Whole-CloudBank equivalence, migration completion, production promotion, and production readiness remain false.

These boundaries are part of the deliverable. They prevent bounded development evidence from becoming an unsupported customer promise.

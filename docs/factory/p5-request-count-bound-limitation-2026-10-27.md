# COUNT-REQUEST-BOUND-01 — proposed wording, not accepted

Numbers proposed for exact approval: margin 2; allowance 1,024 tokens per logical message. The current count request has two logical messages (instructions and input), including when either string is empty. B(q)=2*len(q)+2,048, where q is the exact immutable UTF-8 JSON body sent to the global count endpoint. All model, instructions, input and structured-output schema bytes are included. Whitespace and escaping are counted as actually serialized; no later reserialization supplies the byte count.

Rationale: byte-level merging bounds tokens for the text supplied to that tokenizer by its initial bytes. Doubling the complete wire body supplies an additional full-body allowance for schema rendering. A further 1,024 per message provides fixed framing headroom and avoids a small-input hole. These are deliberately conservative engineering choices, not measured maxima or a proof of server rendering. Structured-output rendering can violate the assumption; the code must detect a returned overrun and stop. The allowance is always charged for both current message slots, so empty instructions do not remove headroom. Other input formats are refused.

At B=1,050,000 the count hold is USD 5.775 at the proposed conservative USD 5.50 per million input tokens. The maximum accepted raw body from the context check is 523,976 bytes. The shared budget can impose a smaller limit: current generation reservation and all previous count holds/charges remain included. There is no separate USD 10 count budget and no change to generation reservation arithmetic. Equality is permitted; exceeding context or cap refuses before the opener.

## Proposed operator decision text

> COUNT-REQUEST-BOUND-01, first COPAU run only: I accept the residual provider assumptions for the exact reviewed request-derived count profile. The controller reserves B(q)=2 times the complete serialized count-request body's UTF-8 byte length plus 1,024 tokens for each of the two logical messages, at USD 5.50 per million input tokens. This is an engineering hold, not a proven ceiling on provider rendering or charges. The run admits at most one count call in flight, performs no count retries, and stops further model transports when a returned count exceeds B or a count result is unavailable/invalid. The count hold remains durable before send; unknown results keep the full hold; returned counts retain their conservative charge and release only excess. billing_final remains false and actual cost is reconciled from the provider invoice. Generation explicitly requests Flex and no automatic tier fallback is allowed. I accept that one detected over-bound or unknown count call may exceed its reserved hold before the controller can stop; the dollar overrun has no demonstrated finite upper bound. Separately, the controller assumes billable input does not exceed a valid returned count. If that assumption is silently violated, excess billing is not observable during the run and may accumulate across completed count calls up to the admitted call limit; the one-call claim does not cover that case. This decision does not accept missing reservations, later-run exposure, other drill gaps, or authorize publication, merge, run, signing or spend by itself.

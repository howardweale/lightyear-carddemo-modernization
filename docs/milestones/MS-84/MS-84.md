## Customer benefit

Turn the differences found in [MS83](../MS-83/MS-83.md) into an explainable upgrade
path. A reviewer can see where the databases started, which scripts ran, which
repairs were necessary, and why each remaining raw difference was accepted.

In beginner terms, both databases begin with comparable data, receive their
respective migration instructions, and are checked again before the next release
proceeds. A difference must either satisfy a specific reviewed rule or be fixed
and measured again. An unexplained difference stops advancement.

## How expected differences are validated

Rules apply only to named fields and observed conditions. They cover fresh,
valid, unique UUIDs; clocks within recorded execution windows; registration paths
matching the actual executed source; timezone values representing the same
instant; and exactly equal finite decimals with different formatting. They do
not globally ignore timestamps, trim business text, or use numeric tolerances.

For example, a hypothetical new metadata row may receive different UUIDs on the
two engines. That can be admitted only when both IDs satisfy the fresh-row rule.
An unexplained change to an existing row's UUID or business value still fails.
Both raw values remain available after acceptance.

Earlier accepted differences carry forward only when their witnesses are bound
to the actual starting snapshots and both raw values remain unchanged. Unknown
tables, columns, row keys or differences block admission. Original rejected
checkpoints remain beside their reviewed successors.

## Repairs and claim boundaries

The replay required explicit corrections, including old-seed prerequisites,
timestamp precision and literal handling, blank-value predicates, missing
dictionary rows, and constraint/index operations incompatible with the observed
starting schema. Native probes, original failures and repair evidence are retained.
The nine earlier application-table findings are resolved on this corrected path.

This proves agreement of complete common base-table data at the declared
checkpoints after documented repairs. Historical release checkpoints do not
provide isolated equivalence proofs for each of the 1,125 script pairs, and the
result is not unmodified-upstream-script equivalence.

Schema equivalence, full application equivalence, platform qualification and
Oracle behavior-catalog native conformance remain unclaimed. The differing
foreign-key counts are visible rather than waived. Static calibration remains
**780 / 111,293 decided SQL units**; native replay does not increase that count.
Running an old seed on Oracle 26ai also does not qualify Oracle 11g or 19c.

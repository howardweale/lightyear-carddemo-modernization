## What the milestone delivers

- A signed MS #63 and MS #57 receipt chain requiring the same evidence key and PostgreSQL image.
- A fresh eight-service target with azn-server, checks, testrunner, creditscore, and chatbot explicitly marked migrated and each generated and executed in a dedicated Java workcell.
- An OAuth-protected Credit Score boundary with a distinct audience and a stable subject-and-UTC-date-bound HMAC result labelled synthetic-v1.
- A runtime-only minimum-length score pepper, no score persistence, and explicit rejection of real credit-bureau or regulated-model claims.
- A distinct-audience Chatbot boundary with system/user prompt separation, input and output limits, instruction-override rejection, and safe model failures.
- Per-authenticated-subject rate limiting and a host/TLS model-egress allowlist that permits plaintext only for allowlisted loopback endpoints.
- Eight executable Spring Boot JARs with zero Oracle and zero MicroTx runtime libraries.
- Twenty-eight bounded scenarios, twenty-one generated Java tests, safe aggregate diagnostics, deterministic contracts, schemas, cross-platform launchers, CI compilation and tests, Control Tower projection, documentation, and adversarial tests.

## How it differs from earlier work

MS #57 qualified the PostgreSQL Customer workcell and MS #63 assembled Authorization, Account, Transfer, Checks, and Test Runner. MS #64 composes all prior targets, explicitly resolves the five remaining services as migrated, and generates and executes each of their target workcells in one eight-service target.

Earlier work remains useful evidence, but it is not automatically promoted into this milestone. A successful parser, simulator, local comparison, or generated artifact is not presented as live platform equivalence or production readiness.

## Boundaries and claims not made

- These boundaries describe MS #64's own evidence scope. Later MS65, MS66 and MS67 receipts add their separate nonproduction qualifications; they do not rewrite this milestone's signed fields.
- Acceptance calls neither a credit bureau nor an external model and persists no prompts, responses, tokens, secrets, peppers, or upstream error details.
- A passing receipt qualifies generation and execution of all five remaining target workcells plus the bounded Credit Score and Chatbot application-control envelope and eight-service package, not a real credit decision or model-answer quality.
- Native Oracle AQ comparison, production data, whole-application Oracle/PostgreSQL equivalence, migration completion, production deployment, promotion, and production readiness remain false.

These boundaries are part of the deliverable. They prevent bounded development evidence from becoming an unsupported customer promise.

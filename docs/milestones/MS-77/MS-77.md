## Binding to the qualified collector

`lightyear_workflow.zosmf_reader.ZosmfReader` sits above the existing
`ZosmfClient` and `ZosmfJobsAdapter`. **`src/lightyear_runtime/zosmf.py` is
unchanged.** Source calls use its read-only GET interfaces only.

The reader chooses the uniquely latest completed run by `exec-ended`, not by
list position or job-ID ordering. Its default owner filter is `*`; supply an
owner to narrow the search. An ambiguous latest run, missing completion time or
possibly truncated listing requires an explicit job ID. The selected job must
match the mapping, have status OUTPUT and retain its return code. A nonzero or
ABEND return code is preserved, never converted into success. Failed selection
clears the previous job context.

The existing client exposes JES spool retrieval, not a catalogued MVS dataset
read operation. This binding therefore supports only **explicitly mapped spool
outputs** of the selected job. A mapping can add, for example:

```json
{
  "datasets": {
    "CARDDEMO.TRANFILE": {"ddname": "TRANSACT", "stepname": "STEP15"},
    "CARDDEMO.ACCTFILE": {"ddname": "ACCTFILE", "stepname": "STEP15"}
  }
}
```

This object supplements the existing graph mapping; it does not replace its job,
steps or DD allocations. Add `procstep` when needed to disambiguate a procedure
step. A dataset must resolve to exactly one spool file with the selected job's
identity and a known record count within the 5,000-record read limit. Missing,
ambiguous, oversized or unbound outputs fail rather than becoming empty data.
The example above is exercised with mock spool outputs; it does not assert that
the existing CardDemo jobs actually retain these datasets in spool. The checked-in
INTCALC collector mapping remains unchanged and contains no such bindings.
POSTTRAN needs its own verified graph/output mapping before collection. Historical
catalogued datasets, generation selection and binary dataset capture remain
unimplemented; reading today's dataset would not prove what a past job consumed.

## Evidence provenance

The reader returns the collector bundle and its `evidence_class`. The source
receipt carries both through. HTTPS alone never upgrades simulated evidence;
`attest_real_zos=True` remains explicit and the existing non-loopback HTTPS gate
is enforced. A boolean is required. These controls implement the collector's
attestation contract; they do not independently prove that a host is z/OS.

Target receipts retain each lane's evidence class. Their combined class cannot
exceed either lane: simulated source or target means **simulated**. Unlabelled
fixture readers default to simulated; unknown classes are refused. Tests of the
explicit `zos_observed` branch use a stub and are propagation tests only, never
a z/OS execution receipt or a qualified baseline.

## Boundaries

- No pack has run against a real z/OS system and no customer pack exists.
- `TargetLane.replay` requires a caller-supplied submit callable; no target
  submission implementation, credential provisioning or scheduler is built.
- Output declarations do not execute sequence, set or summary comparisons.
  No end-to-end batch equivalence verdict or qualification is produced.
- Inputs are declared dataset names, not captured historical input bytes. Their
  transfer and identity binding to target execution remain future work.
- Online transactions and CICS are entirely out of scope. Batch only.
- No workload, platform or milestone status is promoted to proven or done by
  these mock tests. Any technical-deck claim that batch invocation is done
  remains incorrect until the authorised z/OS baseline and remaining execution
  capabilities are demonstrated.

# MS-75 — Four-panel workspace

The Control Tower has four views in order: Work queue, The run, Convergence,
and Discovery. Work queue remains the default. Existing decision credentials,
signatures, approval gates and queue behavior are unchanged.

The run is a read-only projection of `/api/workflow/execution`: completed result
receipts, rounds, block events and receipt-asserted model calls in the verdict
path. Work kinds, before/after transitions and every boundary field are counted
from action receipts. Boolean boundary fields contribute 0 or 1. An absent
boundary measurement is not reported as zero. Missing and invalid journals have
separate empty and unavailable states, without metric cards.

The reference layout is adapted from the supplied `run.reference.js`. Text is
created with DOM nodes and `textContent`; no HTML string rendering is used.
Every selector in `run.css` is scoped to `#run-view`. Tables avoid the shared
`dl` grid rule. The layout adapts to desktop and narrow screens.

Panel switching preserves `controlTowerDecisions.showQueue()` and adds
`showPanel()`. Discovery becomes visible before the scheduled `fitGraph` call.
Existing dense-graph workspace presentation is refreshed on every panel switch.
The run and Convergence refresh when selected. A block's decision button returns
to the current queue without creating or approving a decision.

## Boundaries

- This view describes one recorded run. It does not establish current cloud
  health, fresh execution, production qualification or new semantic equivalence.
- Completed actions are result events, not distinct resolved findings. Block
  counts describe this run, not a live backlog.
- Convergence is the separate MS-73 view. It remains empty until engine recording
  is wired in MS-74. This milestone does not call `RunIndex.record()`.
- The queue is unchanged. Blast radius is not displayed on decision cards;
  the merged radius helper still needs an integration call site.
- No mock measurements, seeded histories, customer journals or preview tools
  are committed. Nothing here has been seen by a customer.
- The committed example can fail replay after source changes because its plan
  binds the Python input tree. It must not be relabeled as verified. A new local
  run over retained evidence may be used for UI validation without cloud calls.

## Verified timeline

The read-only execution response now includes the bounded journal events after
successful deterministic replay. Invalid and missing journals expose no events.
The UI renders round actions, blocks, failures, checkpoints and the terminal halt
in their original order. A compatibility fallback shows recorded blocks if an
older server omits events; it never reconstructs chronology from aggregate counts.
This projection adds no worker, journal write, decision or index-recording path.

## Validation

- A fresh local retained-evidence execution produced 19 completed actions,
  6 rounds, 1 block and 0 receipt-asserted verdict-path model calls.
- Browser inspection confirmed those figures, readable tables at 390px and
  1440px widths, the empty Convergence state, queue navigation from a block,
  and a nonzero fitted Discovery graph after panel switching.
- Browser CI assertions cover all four buttons, empty and invalid run responses,
  visible-before-fit ordering and the compatible `showQueue()` wrapper.
- The existing local decision service is unconfigured; no actual operator
  approval was submitted during UI inspection.
- MS-73 added regression tests after the original handoff, so the old fixed
  1252/21 total is not the current baseline. Validation must report actual totals.

The old fixed 1252/21 handoff total predates MS-73's additional regression
